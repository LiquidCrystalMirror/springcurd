## 二、业务异常体系（exception/目录）

### 2.1 异常类层次结构

```
RuntimeException
  └── BusinessException (基类，含 httpStatus + errorCode)
        ├── BadRequestException       (400) 参数校验失败
        ├── UnauthorizedException     (401) 未登录/Token无效
        ├── ForbiddenException        (403) 权限不足
        ├── NotFoundException         (404) 资源不存在
        ├── ConflictException         (409) 业务冲突（幂等性拦截等）
        └── ServiceUnavailableException (503) 熔断/限流触发
```

### 2.2 原理

- **精准分类**：不同HTTP状态码对应不同异常类，替代原有的 `RuntimeException` 字符串模糊匹配
- **errorCode 字段**：每个异常携带业务错误码（如 `STOCK_INSUFFICIENT`），前端可根据 errorCode 做差异化处理
- **GlobalExceptionHandler 分层处理**：业务异常 → 参数校验 → HTTP层异常 → 数据库异常 → 兜底异常

### 2.3 相关技术

- Spring MVC `@RestControllerAdvice` + `@ExceptionHandler`
- `@ResponseStatus` 设置HTTP响应码

## 三、熔断降级（Resilience4j）

### 3.1 配置文件

`application-resilience4j.yml`，包含四层保护：

| 组件 | 实例名 | 触发条件 | 降级行为 |
|------|--------|----------|----------|
| **CircuitBreaker** | `redisService` | 10次滑动窗口中失败率≥50% | 熔断15秒，返回 "Redis服务暂时不可用" |
| **CircuitBreaker** | `rabbitmqService` | 同上 | 静默跳过（不阻塞主流程），日志记录 |
| **Retry** | `redisRetry` | Redis操作异常 | 最多3次，指数退避 100ms→200ms→400ms |
| **Retry** | `dbRetry` | 数据库操作异常 | 最多3次，指数退避 |
| **RateLimiter** | `orderCreate` | 每秒超过20个请求 | 返回 "请求过于频繁" |
| **RateLimiter** | `loginRateLimit` | 每秒超过5个请求 | 防暴力破解 |
| **TimeLimiter** | `redisTimeLimiter` | 操作超过3秒 | 超时中断 |

### 3.2 原理

- **熔断器（Circuit Breaker）**：三态模型 — CLOSED（正常）→ OPEN（熔断）→ HALF_OPEN（半开探测）
  - 滑动窗口统计失败率，超过阈值自动熔断
  - `waitDurationInOpenState` 后进入半开状态，允许少量请求探测
  - 探测成功则恢复CLOSED，失败则重新OPEN

- **限流器（Rate Limiter）**：令牌桶算法，固定时间窗口内限制请求数

- **重试（Retry）**：指数退避（exponential backoff），避免瞬时故障

### 3.3 服务层封装

`Resilience4jService.java` —— 使用 `@CircuitBreaker`、`@RateLimiter`、`@Retry` 注解，提供：
- `executeRedis()` — Redis操作熔断+重试
- `sendRabbitMessage()` — RabbitMQ熔断（失败静默跳过）
- `executeWithOrderRateLimit()` — 订单限流
- `executeWithLoginRateLimit()` — 登录限流
- `executeDbWithRetry()` — 数据库重试

### 3.4 相关技术

- Resilience4j 是 Netflix Hystrix 的替代品，专为 Java 8+ 函数式编程设计
- 通过 AOP 代理实现，无需侵入业务代码
- 支持 Actuator 端点暴露熔断器/限流器状态：`/actuator/circuitbreakers`、`/actuator/ratelimiters`

## 四、密码安全升级（MD5 → BCrypt）

### 4.1 改动文件

`PasswordUtil.java`

### 4.2 原理

| 特性 | MD5+盐 | BCrypt |
|------|--------|--------|
| 盐值 | 全局固定 | 每次加密随机生成 |
| 计算速度 | 极快（可被暴力破解） | 可调节（cost=10，约0.1s/次） |
| 彩虹表抗性 | 弱 | 强（内置盐值） |
| 密文格式 | 32位hex | `$2a$10$...`（含cost+盐值） |

- **BCrypt 基于 Blowfish 密码算法**，cost 因子为 10 表示 2^10 = 1024 轮迭代
- **向后兼容**：验证时自动识别密文前缀（`$2`开头走BCrypt，否则走MD5），旧密码无需迁移

### 4.3 相关技术

- `spring-security-crypto` 模块（轻量，不含完整Spring Security框架）
- `BCryptPasswordEncoder(10)` — cost=10是行业标准

## 五、健康监控（Spring Boot Actuator）

### 5.1 配置

`application-actuator.yml`

暴露的端点（访问路径 `/actuator`）：
- `/actuator/health` — 健康检查（含Redis、RabbitMQ组件状态）
- `/actuator/health/liveness` — K8s存活探针
- `/actuator/health/readiness` — K8s就绪探针
- `/actuator/metrics` — JVM、HTTP、数据库指标
- `/actuator/prometheus` — Prometheus格式指标
- `/actuator/circuitbreakers` — 熔断器状态

### 5.2 原理

- Actuator 通过 `HealthIndicator` 接口自动检测各组件状态

- Prometheus endpoint 可对接 Grafana 实现可视化监控大盘

## 六、链路追踪（TraceId）

### 6.1 实现

`TraceIdFilter.java` — `javax.servlet.Filter`

### 6.2 原理

```
请求进入 → TraceIdFilter 生成16位UUID作为TraceId
         → 写入 MDC("traceId")
         → 写入响应头 X-Trace-Id
         → 所有日志自动带上 [TraceId:xxx]
         → 支持跨服务传递（从请求头 X-Trace-Id 读取）
```

### 6.3 日志格式变化

```
旧: 2026-07-14 10:00:00.000 [main] INFO  c.x.Service - [Category:order.redis] [BizNo:123] 处理订单
新: 2026-07-14 10:00:00.000 [main] INFO  [TraceId:a1b2c3d4] c.x.Service - [Category:order.redis] [BizNo:123] 处理订单
```

### 6.4 面试意义

- 分布式链路追踪的基础设施（可扩展为集成 SkyWalking / Zipkin）
- 通过 `%X{traceId}` 在 logback 中输出，无需修改业务代码
- 前端拿到 `X-Trace-Id` 响应头，反馈问题时附带，后端可快速定位日志

## 八、RabbitMQ 开发环境优化

`application-rabbitmq.yml` 新增：
```yaml
listener:
  simple:
    auto-startup: ${RABBITMQ_LISTENER_AUTO_START:false}
```

- 默认不启动监听器，避免本地无 RabbitMQ 时日志刷屏
- 生产环境设置环境变量 `RABBITMQ_LISTENER_AUTO_START=true` 即可启用
