# 本地消息表与可靠性投递设计

> 面试要点：MQ 消息丢失怎么办？本地消息表模式 vs 事务消息的区别？业务和消息如何保证一致性？

---

## 一、问题背景

### 1.1 为什么需要可靠消息投递？

本项目中，订单创建后的流程是：

```
Redis 库存扣减成功 → 发送 MQ 消息 → MQ 消费者将订单详情持久化到 MySQL
```

**可能的消息丢失场景**：
- 扣减成功后，发 MQ 时网络闪断 → 消息丢失
- RabbitMQ Broker 宕机（未配置持久化队列）
- 生产者代码抛异常，消息根本没发出去

如果消息丢失，结果是：**Redis 库存已经扣了，但 MySQL 中没有订单记录**——数据不一致。

### 1.2 理想的解决方案：事务消息（RocketMQ 特有）

RocketMQ 支持事务消息：

```
发送 Half 消息 → 执行本地事务 → 提交/回滚
```

但 RabbitMQ **不支持**事务消息。因此需要自己实现补偿机制。

## 二、本地消息表模式

### 2.1 核心思想

> 先写数据库，再发消息，发完更新状态。数据库的持久性保证消息不丢。

### 2.2 消息表结构

```sql
rabbit_message_log:
┌──────────────┬──────────────┬─────────────────────────┐
│ 字段          │ 类型          │ 说明                     │
├──────────────┼──────────────┼─────────────────────────┤
│ id           │ BIGINT        │ 主键（雪花ID）            │
│ message_id   │ VARCHAR(64)   │ 消息唯一ID（UUID）        │
│ exchange     │ VARCHAR(128)  │ 交换机名称                │
│ routing_key  │ VARCHAR(128)  │ 路由键                    │
│ message_body │ TEXT          │ 消息体 JSON（完整保存）    │
│ status       │ INT           │ 0=待发送 1=成功 2=失败    │
│ retry_count  │ INT           │ 已重试次数                │
│ error_msg    │ VARCHAR(1024) │ 失败原因                  │
│ create_time  │ DATETIME      │ 创建时间                  │
│ update_time  │ DATETIME      │ 更新时间                  │
└──────────────┴──────────────┴─────────────────────────┘
```

### 2.3 投递流程

```
业务操作成功（Redis 扣减完成）
  │
  ▼
┌──────────────────────────────┐
│ ① 序列化消息体为 JSON          │
│    ObjectMapper.writeValueAsString(message)        │
│    失败 → 记录 error 日志 → return（不抛异常）      │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ ② 写入本地消息表               │
│    INSERT INTO rabbit_message_log (status=0)        │
│    失败 → 异常向上传播 → 业务层 catch 记录 warn     │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ ③ 发送到 RabbitMQ             │
│    rabbitTemplate.convertAndSend(...)               │
│    成功 → UPDATE SET status=1 WHERE message_id=?    │
│    失败 → UPDATE SET status=2, error_msg=?          │
└──────────────────────────────┘
```

### 2.4 状态流转

```
       _____________
      │   创建消息    │
      │  status = 0  │
      └──────┬───────┘
             │
      ┌──────┴───────┐
      ▼              ▼
  ┌──────────┐  ┌──────────┐
  │ 发送成功  │  │ 发送失败  │
  │status=1  │  │status=2  │
  └──────────┘  └────┬─────┘
                     │
              ┌──────┴───────┐
              │ 定时任务扫描   │
              │ status=0或2   │
              │ → 重新发送     │
              └──────────────┘
```

## 三、业务集成

### 3.1 业务层的容错设计

```java
// 订单扣减成功后
try {
    rabbitMQDemoProducer.sendDeduct(bizNo, platformId, operations);
} catch (Exception e) {
    // 不影响主流程！接口已经返回成功
    StructuredLogger.warn("RabbitMQ扣减消息发送异常（不影响业务）: {}", e.getMessage());
}
```

**设计原则**：MQ 发送失败**不影响接口返回**。因为：
- Redis 库存已经扣减成功（用户侧的核心操作已完成）
- 消息表中有记录（status=2），后续可以补偿
- 如果因为 MQ 问题回滚 Redis → 用户体验更差

### 3.2 三个业务入口

| 方法 | 触发时机 | 路由键 |
|------|----------|--------|
| `sendDeduct()` | 订单 Redis 扣减成功 | `demo.routing.deduct` |
| `sendAdd()` | 补货 Redis 增加成功 | `demo.routing.add` |
| `sendRollback()` | 取消订单 Redis 回滚成功 | `demo.routing.rollback` |

## 四、与事务消息的对比

| 特性 | 本地消息表 | RocketMQ 事务消息 | RabbitMQ 事务 |
|------|-----------|-------------------|---------------|
| 实现复杂度 | 中（需建表+补偿任务） | 低（API 内置） | 低（channel.txSelect） |
| 性能 | 高（异步发送） | 高 | 低（同步确认，吞吐量骤降） |
| 消息可靠性 | 高（DB持久化） | 高（Broker 持久化） | 中（仅保证投递到 Broker） |
| 适用场景 | RabbitMQ/任何 MQ | 仅 RocketMQ | 不推荐生产使用 |

**本项目选择本地消息表的依据**：
- 使用 RabbitMQ（不支持事务消息）
- 本地消息表的 DB 写入开销可接受（相比业务操作，一次 INSERT 开销极小）
- 消息体完整保存，出问题时可以回溯

## 五、已知局限与改进方向

### 5.1 当前未实现的

- **定时补偿任务**：status=0 或 status=2 的记录需要定时扫描重发（当前靠人工排查）
- **消息去重**：消费者端未做消息幂等（因为当前消费者只打日志不做业务）

### 5.2 改进方向

```
改进 1：加 Quartz/XXL-Job 定时任务
  每 5 分钟扫描 status IN (0, 2) 且 create_time < NOW() - 5 MINUTE 的记录
  → 重新发送 → 更新 status

改进 2：设置最大重试次数
  retry_count >= 10 → 标记为 status=3（人工介入）
```

## 六、面试常见追问

### Q1: 步骤②（写消息表）和步骤③（发 MQ）之间，服务挂了怎么办？

消息表中有记录（status=0），但消息没发出去。定时补偿任务会扫描到它并重发。

### Q2: 消息表写入成功，MQ 发送成功，但更新 status 时失败了？

消息已经投递到 RabbitMQ，但消息表还显示 status=0。定时补偿任务会重发这条消息 → **消费者需要做幂等**。

### Q3: 为什么不在数据库事务中完成（写业务数据 + 写消息表）？

当前 Redis 库存操作和 MySQL 是异构存储，无法放在同一个数据库事务中。改进方向：
- 用 Redis 的事务（MULTI/EXEC）做本地"事务"
- 或改用 Seata 分布式事务（重量级）
