# 双重幂等保护设计

> 面试要点：为什么需要两层幂等？Redis TTL 过期后如何防止重复扣减？数据库唯一索引和业务逻辑如何配合？

---

## 一、问题背景

### 1.1 什么是幂等，为什么需要？

幂等（Idempotent）：同一个操作执行一次和执行多次，结果相同。

在库存扣减场景中：
- 用户点击"下单"按钮 → 网络超时 → 用户再次点击
- 前端防重失效 → 同一个订单号发了两次请求
- MQ 消费者重试 → 同一条消息被消费多次

**如果接口不幂等**：重复的订单号会导致库存被扣减两次 → 超卖。

### 1.2 单层幂等的缺陷

如果只用 **Redis 幂等 Key + TTL**：

```
订单创建成功 → SET biz:idempotent:deduct:ORD001 = "success" EX 3600
                → 1小时内，重复请求被拦截 ✅

1小时后，TTL 过期，Key 被删除：
                → 网络重试的请求再次到达
                → Redis 中找不到幂等标记 → 判定为新请求 → 再次扣减库存 ❌ 超卖！
```

**根本问题**：Redis 的 TTL 机制不适合做永久幂等记忆，但设置永不过期又会导致内存膨胀。

## 二、设计思路

### 2.1 两层幂等架构

```
请求进入
  │
  ▼
┌─────────────────────────────────────┐
│  第一层：Redis 幂等（快速路径）       │
│  Key: biz:idempotent:{opType}:{bizNo}│
│  TTL: 配置值（默认3600秒）            │
│                                     │
│  HIT → 命中，直接返回幂等拦截          │
│  MISS → 未命中，进入第二层检查         │
└────────────────┬────────────────────┘
                 │ MISS
                 ▼
┌─────────────────────────────────────┐
│  第二层：MySQL 幂等表（永久路径）     │
│  表: biz_idempotent                  │
│  唯一索引: UNIQUE(biz_no, op_type)   │
│                                     │
│  HIT → 命中，返回幂等拦截             │
│  MISS → 确认是新请求，继续执行         │
└─────────────────────────────────────┘
```

### 2.2 各层职责

| 层级 | 存储 | 速度 | 持久性 | 作用 |
|------|------|------|--------|------|
| Redis 层 | 内存 | 微秒级 | TTL 过期 | 拦截99%的重复请求，高性能 |
| MySQL 层 | 磁盘 | 毫秒级 | 永久 | 兜底保护，防止 TTL 过期后的重复请求 |

### 2.3 状态码定义

```
biz_idempotent 表：
  status = 0  → 处理中（事务还未完成）
  status = 1  → 成功
  status = 2  → 失败
```

- 查询时条件：`WHERE biz_no = ? AND op_type = ? AND status = 1`
- 只有 `status = 1`（成功）才判定为幂等命中
- `status = 0` 说明有并发请求正在处理中（极少数情况）

## 三、执行流程

### 3.1 下单接口的完整幂等流程

```
processOrder(orderDTO):
  
  ① Redis 幂等检查（在 Lua 脚本内完成）
     │
     ├─ 命中 "already_success" → 返回 409 "订单已存在，请勿重复提交"
     │
     └─ 未命中 → Lua 脚本继续执行扣减
                  → 扣减成功后 SET biz:idempotent:deduct:{bizNo} = "success"
                  → 返回 success → 接口返回 200
                  
  ② MySQL 幂等写入（订单持久化时由 MQ 消费者完成）
     │
     消费者收到消息 → INSERT INTO biz_idempotent(biz_no, op_type, status)
     │                → 利用唯一索引 (biz_no, op_type) 防重
     │
     └─ 如果 Redis TTL 过期，重复请求到达：
          → Redis 层 MISS（Key 已过期）
          → 业务层查询 MySQL biz_idempotent 表
          → 发现记录存在且 status=1 → 返回幂等拦截
```

### 3.2 数据库唯一索引的并发保护

```sql
CREATE TABLE biz_idempotent (
    id BIGINT PRIMARY KEY,
    biz_no VARCHAR(64) NOT NULL,
    op_type VARCHAR(32) NOT NULL,
    status INT DEFAULT 0,
    create_time DATETIME,
    UNIQUE KEY uk_biz_op (biz_no, op_type)
);
```

**关键**：唯一索引 `uk_biz_op` 在数据库层面保证了同一 `(biz_no, op_type)` 组合只会插入一条记录。

即使 Redis TTL 过期后，两个重复请求同时到达：
```
请求A → 先执行 INSERT → 成功
请求B → 同时执行 INSERT → 唯一索引冲突 → 抛出 DuplicateKeyException
                          → 再次查询 → 发现已有记录且 status=1
                          → 返回幂等拦截
```

## 四、与其他方案的对比

| 方案 | 优点 | 缺点 | 本项目选择 |
|------|------|------|------------|
| 纯 Redis 幂等 | 极快 | TTL 过期后失效 | ❌ |
| 纯 MySQL 幂等 | 永久可靠 | 每次都要查DB | ❌ |
| Redis + MySQL 双层 | 兼顾速度与可靠性 | 实现稍复杂 | ✅ |
| 分布式锁 | 灵活 | 锁超时、死锁风险 | ❌ |

## 五、取消订单的幂等

取消操作也有独立的幂等 Key：

```
Redis: cancel:idempotent:{bizNo}
MySQL: biz_idempotent (op_type = 'cancel')
```

取消时的幂等逻辑：
- 如果已经取消过（`status = 2`）→ 返回 "已取消"
- 如果没有 → 执行取消流程 → 写 Redis 幂等标记 → MQ 消费者写 MySQL 幂等记录

## 六、面试常见追问

### Q1: Redis 和 MySQL 的幂等记录时间差怎么办？

在扣减成功的瞬间（Redis Lua 脚本内），Redis 幂等标记已经写入。后续的重复请求（TTL 过期前）都会被 Redis 层拦截。

TTL 过期后的时间差窗口：
- 重复请求到达 → Redis MISS → 查 MySQL → 如果 MySQL 中还没有记录（消费者延迟）→ **极小概率会重复扣减**

缓解措施：
- 消费者延迟通常在 2-4 秒
- Redis TTL 设置为 3600 秒（1 小时）
- TTL 预期能覆盖 99.99% 的重复请求

### Q2: 如果 Redis 宕机，幂等完全依赖 MySQL？

是的。此时 Redis 层失效，所有请求都穿透到 MySQL 层。MySQL 唯一索引依然能保证幂等，只是多了一次数据库查询的开销。

### Q3: biz_idempotent 表会不会无限增长？

需要定期清理。建议：
- 保留 90 天内的记录
- 超过 90 天的记录可以归档或删除
- `status = 0`（处理中）的记录需要特别关注
