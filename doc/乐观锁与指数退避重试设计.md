# 乐观锁与指数退避重试设计

> 面试要点：乐观锁 vs 悲观锁的区别？version 字段如何防并发？指数退避重试为什么比固定间隔好？

---

## 一、问题背景

### 1.1 并发更新 product_stock 表的冲突

取消订单时，需要更新 `product_stock` 表（MySQL 中的库存备份表）：

```
线程 A: 读到 stock=100, version=1 → UPDATE SET stock=95, version=2 WHERE version=1
线程 B: 读到 stock=100, version=1 → UPDATE SET stock=90, version=2 WHERE version=1
```

如果线程 B 在线程 A 之后执行，`WHERE version=1` 已经找不到记录了（已经被 A 更新为 version=2）→ B 更新失败 → **丢失更新**。

### 1.2 乐观锁 vs 悲观锁

| 特性 | 乐观锁 | 悲观锁（SELECT FOR UPDATE） |
|------|--------|---------------------------|
| 原理 | 版本号对比，冲突时重试 | 数据库行锁，阻塞其他事务 |
| 并发性能 | 高，无锁等待 | 低，串行化执行 |
| 适用场景 | 读多写少，冲突概率低 | 写多，冲突概率高 |
| 实现复杂度 | 需手动处理重试 | 简单，数据库自动处理 |

**本项目选择乐观锁的原因**：
- 库存表更新频率不高（主要是取消订单和补货时触发）
- 乐观锁无需占用数据库连接等待
- 配合重试机制，冲突时自动恢复

## 二、实现细节

### 2.1 表结构

```sql
CREATE TABLE product_stock (
    product_id BIGINT PRIMARY KEY,
    stock INT NOT NULL,
    version INT DEFAULT 0,   -- 乐观锁版本号
    update_time DATETIME
);
```

### 2.2 更新 SQL

```sql
UPDATE product_stock 
SET stock = ?, version = version + 1, update_time = NOW()
WHERE product_id = ? AND version = ?
```

**关键**：`WHERE version = ?` 确保了只有版本号匹配时才能更新成功。

### 2.3 Java 侧重试逻辑

```java
private void updateProductStockFromRedis(Long productId) {
    // 1. 从 Redis 读取最新库存值
    String stockStr = redissonClient.getBucket("product:stock:" + productId).get();
    int currentStock = Integer.parseInt(stockStr);
    
    // 2. 查询 product_stock 记录（含 version）
    ProductStock stock = productStockMapper.queryById(productId);
    
    // 3. 乐观锁更新（最多重试 3 次）
    int maxRetries = 3;
    for (int i = 0; i < maxRetries; i++) {
        int currentVersion = stock.getVersion();
        int rows = productStockMapper.updateStockWithVersion(
            productId, currentStock, currentVersion
        );
        
        if (rows > 0) {
            return; // 成功
        }
        
        // 冲突：重新查询最新版本号
        if (i < maxRetries - 1) {
            Thread.sleep(10L * (i + 1));  // 指数退避: 10ms → 20ms → 30ms
            stock = productStockMapper.queryById(productId); // 重新查
        }
    }
    
    // 全部重试失败 → 抛异常
    throw new RuntimeException("乐观锁重试失败");
}
```

## 三、指数退避重试

### 3.1 为什么用指数退避？

| 重试策略 | 间隔 | 优缺点 |
|----------|------|--------|
| 固定间隔 | 每次等 100ms | 简单，但冲突时所有线程同时重试 → 再次冲突 |
| 线性增长 | 100ms → 200ms → 300ms | 较好，分散重试时间 |
| **指数退避** | **100ms → 200ms → 400ms** | **最佳**，冲突概率指数级下降 |
| 随机抖动 | 100ms + 随机(0~50ms) | 最好，完全避免惊群效应 |

本项目使用**线性增长**（`baseInterval * (retry + 1)`），简单实用。如果后续压测发现惊群效应，可改为指数退避。

### 3.2 项目中的重试场景

| 位置 | 重试次数 | 退避策略 | 失败处理 |
|------|----------|----------|----------|
| Lua 脚本执行 | 3 次 | 100ms→200ms→300ms | 回退到直接执行脚本内容 |
| Redis 取消操作 | 3 次 | 100ms→200ms→300ms | 抛异常，中断取消流程 |
| DB 更新（取消订单） | 3 次 | baseInterval × (retry+1) | 记录严重错误日志，需人工介入 |
| product_stock 乐观锁 | 3 次 | 10ms→20ms→30ms | 抛异常 |

### 3.3 取消订单中的重试链路

```
cancelOrder() 
  → DB 更新 order_detail 表（带重试 3 次，指数退避）
    成功 → 更新 product_stock 表
            → 乐观锁冲突 → 重试 3 次（10ms→20ms→30ms）
              成功 → 完成
              失败 → 记录【严重错误-需人工介入】
    失败 → 记录【严重错误-需人工介入】Redis 已回滚但 DB 未更新
```

## 四、数据一致性保障

### 4.1 取消订单的三端一致性

```
操作顺序（关键！）：
  ① Lua 脚本恢复 Redis 库存（原子操作，必须成功）
  ② 更新 order_detail 表 status → 0（带重试）
  ③ 更新 product_stock 表（乐观锁+重试）
```

如果步骤 ②③ 失败，Redis 已回滚但 DB 未更新 → **数据不一致**。日志中标记 `【严重错误-需人工介入】`，需要运维手动修复。

**为什么不同时回滚 Redis？** 因为 Redis 操作和 MySQL 操作不在同一事务中，无法统一回滚。这是一个已知的分布式事务问题，需要在更高层面解决（如引入 Seata TCC 或 Saga 模式）。

### 4.2 当前方案的分级

```
正常路径（95%+）：
  Redis ✅ → DB ✅ → product_stock ✅

异常路径（需重试）：
  Redis ✅ → DB 第1次❌ → 重试 → ✅ → product_stock ✅

严重异常（需人工介入）：
  Redis ✅ → DB 3次重试❌ → product_stock ❌ → 告警
```

## 五、面试常见追问

### Q1: 乐观锁重试次数怎么确定的？

3 次是一个经验值。太少（如 1 次）容易因瞬时冲突失败，太多（如 10 次）可能长时间阻塞请求。如果生产环境冲突频率高，可调整为 5 次并加随机抖动。

### Q2: 为什么不直接用 Redisson 分布式锁？

可以，但：
- 分布式锁会增加一次 Redis 网络往返
- 有锁超时和误删风险
- product_stock 表的更新不是热点操作，乐观锁足够

### Q3: 乐观锁适合读多写少的场景，那如果写入频繁怎么办？

如果 product_stock 表的写入变得频繁（如秒杀场景），应该：
1. 将 product_stock 的更新也移到 Redis Lua 脚本中
2. 或使用悲观锁（SELECT FOR UPDATE）
3. 或拆表，按商品 ID 分片降低冲突概率
